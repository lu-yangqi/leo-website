# Leo Personal Website - v5.2

## Task

Implement Version 5.2 of the personal website.

The goal of this version is to improve the reading experience of technical blog articles.

Version 5.1 should already provide:

* `/blog` article list
* Dynamic routes such as `/blog/[slug]`
* Markdown article rendering
* BlogCard links to article pages
* Blog post loading by slug
* Basic article layout

Version 5.2 should improve the existing system rather than redesign or replace it.

The main goals are:

1. Add syntax highlighting for code blocks
2. Add article tags
3. Improve Markdown typography
4. Improve article metadata presentation
5. Add a clear "Back to Blog" navigation link

Keep this version focused on article reading experience.

---

# Current Blog Flow

The existing flow should remain:

```text
content/blog/*.md

        ↓

lib/blog.ts

        ↓

/blog

        ↓

BlogCard

        ↓

/blog/[slug]

        ↓

Rendered Markdown article
```

Version 5.2 should enhance this architecture without unnecessarily rewriting it.

---

# Requirement 1 — Add Syntax Highlighting

Technical articles will contain code in languages such as:

```text
Python
C++
JavaScript / TypeScript
Bash / PowerShell
HTML
CSS
SQL
Assembly
```

Markdown code blocks may look like:

````markdown
```python
model = MyModel()
````

````

or:

```markdown
```bash
git add .
git commit -m "update"
git push
````

````

Add syntax highlighting to fenced Markdown code blocks.

## Implementation Guidance

First inspect the Markdown rendering solution already implemented in Version 5.1.

Extend the existing Markdown pipeline instead of replacing it unnecessarily.

If the current renderer is compatible with the unified / rehype ecosystem, a lightweight highlighting plugin may be used.

Choose a small, well-maintained solution that fits the existing architecture.

Do not add a large documentation or blog framework only for syntax highlighting.

---

## Code Block Requirements

Code blocks should:

- Clearly differ from normal article text
- Preserve indentation
- Use a readable monospace font
- Support horizontal scrolling when code is too wide
- Never cause the entire page to overflow horizontally
- Work correctly on mobile
- Preserve the declared language where possible

Inline code should remain visually different from fenced code blocks.

Example:

```text
npm run dev
````

should appear as inline code.

A multiline code example should appear as a separate code block.

Convert the tag string into:

```ts

```

inside the blog data layer.

# Requirement 6 — Improve Markdown Typography

Improve the visual styling of rendered Markdown content.

The goal is to make long technical notes comfortable to read.

Support good typography for:

* h1
* h2
* h3
* paragraphs
* unordered lists
* ordered lists
* links
* bold text
* italic text
* inline code
* fenced code blocks
* blockquotes
* horizontal rules

If tables are already supported by the Markdown renderer, make sure they remain readable.

Do not add a major new Markdown feature only to support tables.

---

# Heading Design

Headings should have a clear visual hierarchy.

For example:

```text
Article Title
    ↓

H1 section
    ↓

H2 subsection
    ↓

H3 smaller subsection
```

Avoid excessive font sizes.

Spacing should make article structure easy to scan.

---

# Paragraph Design

Paragraphs should:

* Have comfortable line height
* Have readable spacing
* Avoid extremely long line lengths
* Remain readable on desktop and mobile

Keep the existing article reading width if Version 5.1 already implemented a good one.

Do not redesign the overall website width without a clear reason.

---

# Lists

Lists should have:

* Clear indentation
* Proper spacing between items
* Correct bullet / number visibility

Nested lists should remain readable if supported.

---

# Links

Links inside Markdown articles should:

* Be visually identifiable
* Have a clear hover state
* Have a keyboard focus state
* Remain accessible

Do not make normal article links look identical to normal paragraph text.

---

# Blockquotes

Markdown such as:

```markdown
> This is an important observation.
```

should have a clear but subtle visual treatment.

Keep the design minimal.
